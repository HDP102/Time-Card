The reasoning behind what we did
Decision	Why
FireMon got its own ICS ruleset; GoAlert went hybrid	FireMon’s Azure VMs have no Core ruleset to extend. GoAlert has an existing Core ruleset, so we added the ICS scope there, per your correction.
Removed the 7 server IP lists	IP lists only match unknown addresses, never a known resource. We confirmed this in Draft View in both directions, and Nick confirmed it. Servers use their labels.
Outbound rules live in the destination’s ruleset (Mainframe, Exchange, Check Point, Vendor B2B, storage)	In a scoped ruleset, extra-scope only frees the source. The destination has to be in scope, so the rule belongs to the app being reached. All of these now show Allowed in Draft View.
Network devices on an IP list	Routers, switches and APICs aren’t workloads or ICS resources, so there’s no label to use. That’s the case IP lists are for. Nick’s guidance covered servers. All 12 IPs were checked with znslookup and are FireMon-managed Cisco gear.
That rule is Intra-Scope	The source (FireMon) is inside the scope. Extra-Scope would let Server from anywhere use it.
Intra rule is Server → Server, not picked VMs	The version built from picked VMs still showed Denied. The label version shows Allowed (15k flows).
Mainframe NTP destination has two roles	sys3 is R: Server and zos is R: Single Node App. With only one role, zos would be missed.
Approved app definitions (Illumio Cloud Secure, Qualys)	Labels don’t apply until a deployment is approved, so the rules had nothing to match. We approved after getting the OK.
Fix the tag, not the definition (Check Point)	A discovery rule created the ICS_Checkpoint definition, and it matches Application = Checkpoint. The VMs say CheckPointUtility. Fixing the tag keeps the definition clean.
DC NetBIOS (137) left blocked	FireMon doesn’t need it.
Nothing provisioned	Everything is drafted for your review. Only our own items were touched, and never select-all, since other people’s drafts are pending.

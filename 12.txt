1. AD DNS: add an ICS scope to A: Active Directory?

What we saw: FireMon → v50dclwin021/022 on 53 UDP is the biggest denied flow (about 25k flows a day). In ICS those DCs carry ICS_Active Directory + Production + Domain Controller.
Why I’m asking: the rule has to live in the destination’s ruleset. The only AD ruleset is A: Active Directory: 31 rules, scoped to all environments. Adding an ICS scope there means all 31 rules start applying to the Azure DCs. That changes things for every app, so I didn’t want to do it without you.
What I’d propose: add ICS_Active Directory + Production as a second scope (the GoAlert pattern) and add the FireMon DNS rule.
If he asks “why not put it in the FireMon ruleset?” Extra-scope only frees the source. The destination still has to be inside the ruleset’s scope, and the DCs aren’t in FireMon’s.

2. Qualys: one global rule or per-ruleset?

What we saw: the Qualys scanner v50secapl002 was hitting FireMon on about 40 ports and getting denied. It only got ICS labels (ICS_Qualys + Production) after we approved its app definition.
Why I’m asking: I added ICS_Qualys → All Services in FireMon, GoAlert and PhishER. Every app will need the same rule, so copying it into every ruleset doesn’t scale.
What I’d propose: one global rule, the same way Core probably handles Qualys today.
If he asks “why All Services?” A vulnerability scanner probes every port. Limiting it defeats the scan.

3. Is the network devices IP list an OK exception?

What we saw: after we removed the server IP lists, FireMon traffic to 12 IPs was denied. That was SSH to routers and switches and 443 to two Cisco APICs. None of them are in Illumio inventory or workloads, and all are FireMon-managed devices (confirmed with znslookup).
Why I’m asking: Nick said no IP lists, but his example was servers. These are network gear with no VEN and no ICS resource, so there’s no label to use.
What I’d propose: keep IPL: FireMon Managed Network Devices and build it out from FireMon’s device inventory export.
If he asks “who maintains it?” We do, since FireMon is ours. Re-sync it from the FireMon inventory whenever devices are added.

4. Is it OK to add rules to auto-generated ICS rulesets?

What we saw: FireMon SSH to the Vendor B2B VPN appliances was denied. There’s no Core Vendor B2B ruleset, only an empty, auto-generated App: ICS_Vendor B2B Env: Production.
Why I’m asking: I put the rule in the auto-generated ruleset and it now shows Allowed. You mentioned before that those rulesets can’t be removed, so I don’t know whether ICS overwrites them or whether they’re meant to stay empty.
If he says no: we’d need a proper Vendor B2B ruleset. Ask who owns creating it.

5. Check Point Azure VMs: OK to change the tag?

What we saw: FireMon → v51secapl007/008 on 18184 (log collection) is denied, about 5k flows. In ICS they have no app label. The ICS_Checkpoint definition matches Application = Checkpoint, but the VMs are tagged CheckPointUtility, so the definition shows 0 resources.
Why I’m asking: fixing the tag is cleaner than editing a definition a discovery rule created. Changing the Application tag could affect anything else keyed on it, though, and I don’t have Azure rights (401).
What I’d propose: change the tag to Checkpoint, then add an ICS scope to A: Checkpoint | E: Production. The on-prem Check Point rule already works.

PG&E Entra ID Client Credential OAuth Flow 
This document provides steps to perform certificate-based client authentication for OAuth flow. 

Certificate based authentication is a secure authentication than the traditional password/secret-based authentication. 

Since Entra ID (formerly known as Azure AD) will be PG&E’s new Identity provider aka OAuth authorization server, this document will focus on integration with Entra ID.  

Client authentication is important in the OAuth flow. It becomes more important in Client Credentials grant flow because of it being the only authentication requirement to obtain bearer token. 

 



Steps to obtain Bearer token in Client credentials OAuth flow - 
 



1.Generate a certificate:  
OAuth clients will need to generate a certificate and share the public cert with Azure SSO team. SSO team will upload the public cert in the Entra ID for the OAuth connection. OAuth client in this case is the application trying to obtain bearer token from Entra ID. 
Certificate for non-prod connection can be self-signed. For prod certificate should be CA signed (can be internal PG&E CA signed). CN and DNS value of the certificate should be in the format - {App ID}-{Application Name}.EntraID.AuthN.pge.com
Tip: Use tools like OpenSSL to generate the certificate.
                  

openssl req -x509 -sha256 -nodes -days 365 -newkey rsa:4096 -keyout private.key -out mycert.crt



2.Obtain the x5t header parameter for the JWT: 
X5t is Base64url-encoded SHA-1 thumbprint of the X.509 certificate's DER encoding. 
Tip: OpenSSL has commands to generate x5t. one such command is - echo $(openssl x509 -in mycert.crt -fingerprint -noout) | sed 's/SHA1 Fingerprint=//g' | sed 's/://g' | xxd -r -ps | base64 
 

3.Construct JWT:  
 

JWT has 3 parts – 

 a. Header: It contains the information about the key and the algorithm used to generate the signature. 

 

Sample header- 

  { 

  "alg": "RS256", 

  "typ": "JWT", 

  "x5t": "Py3f8vKDUjR3bqfUhzMIyOb8XuM=" 

} 

 

Parameter  

Remark 

alg 

Should be RS256 

typ 

Should be JWT 

X5t 

Explained in step#2 , Base64url-encoded SHA-1 thumbprint of the X.509 certificate's DER encoding. 

 

 b. Pay load: Contains set of claims. 

Sample payload - 

{ 

  "aud": "https://login.microsoftonline.com/e84bb675-81b1-4f49-985b-3e2d77c6c94d/oauth2/v2.0/token", 

  "exp": 1689303330, 

  "iss": "c1127ab5-330a-46ed-b6a9-039795748df9", 

  "jti": "22b3bb26-e046-42df-9c96-65dbd72c1c81", 

  "nbf": 1484592741, 

  "sub": "c1127ab5-330a-46ed-b6a9-039795748df9", 

   "iat": 1484592741, 

} 

 

Claim 

Sample value 

Description 

aud 

https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token 

The "aud" (audience) claim identifies the recipients that the JWT is intended for (Azure AD) 

exp 

 

The "exp" (expiration time) claim identifies the expiration time on or after which the JWT MUST NOT be accepted for processing. See RFC 7519, Section 4.1.4. This allows the assertion to be used until then, so keep it short - 5-10 minutes after nbf at most. Azure AD does not place restrictions on the exp time currently. 

Iss  

ClientID 

The "iss" (issuer) claim identifies the principal that issued the JWT, in this case your client application. Use the GUID application ID. 

jti 

 

The "jti" (JWT ID) claim provides a unique identifier for the JWT. The identifier value MUST be assigned in a manner that ensures that there is a negligible probability that the same value will be accidentally assigned to a different data object; if the application uses multiple issuers, collisions MUST be prevented among values produced by different issuers as well. The "jti" value is a case-sensitive string. RFC 7519, Section 4.1.7 

nbf 

 

The "nbf" (not before) claim identifies the time before which the JWT MUST NOT be accepted for processing. RFC 7519, Section 4.1.5. Using the current time is appropriate. 

sub 

ClientID 

The "sub" (subject) claim identifies the subject of the JWT, in this case also your application. Use the same value as iss. 

iat 

 

The "iat" (issued at) claim identifies the time at which the JWT was issued. This claim can be used to determine the age of the JWT. RFC 7519, Section 4.1.5. 

 

 

c. Signature:  Signature allows a JWT to be validated against modifications and it confirms the authenticity of the JWT.  

 

4. Call Entra ID to obtain bearer token: 
 

Make a POST call to Entra ID token end point - https://login.microsoftonline.com/{tenant ID}/oauth2/v2.0/token with following OAuth parameters in the body. 

 

client_id – This is the client identifier. The value for this parameter will be provided by Azure SSO team. 

grant_type=client_credentials 

scope - This defines the access granted to the bearer token. The value for this will be provided by Azure SSO team. 

client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer 

client_assertion – Base 64 encoded JWT constructed in step#3 above. 

 

 

If OAuth parameters in the request are correct and authentication is successful, Entra ID will provide access token in response.
